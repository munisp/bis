CI/CD SEPARATES REVERSIBLE ROLLOUT FROM DATA CHANGE

[09]
SOURCE GATE [01]

VALIDATE THE CANDIDATE

Run type, unit, integration, build, migration-manifest, Helm render, policy, and dependency-security checks.
Use disposable PostgreSQL for compatibility tests; do not mutate a shared staging database in pull-request CI.
Require review and provenance before a deployment workflow may assume cloud identity.
→
RELEASE GATE [02]

DEPLOY WITH SHORT-LIVED IDENTITY

GitHub Actions OIDC exchanges repository and environment claims for a narrowly scoped workload identity.
Helm renders a versioned release, then uses `--atomic --wait` for reversible resource rollout.
Canary health includes BFF readiness, synthetic login, refresh contract, and alert receiver checks.
→
DATA GATE [03]

ADVANCE COMPATIBILITY IN PHASES

Expand first, backfill in short idempotent batches, and run dual-compatible BFF behavior.
Activate only after observed evidence; contract only after legacy traffic reaches zero and restore rehearsal passes.
Data rollback is logical containment and compatibility restoration—not an unsafe destructive schema reversal.

REVERSIBLE DELIVERY

Application image, Helm values, traffic split, and feature flag revert through a protected rollout path.

CONTROLLED DATA EVOLUTION

Schema phase transitions require separate evidence, approval, backup/restore proof, and an explicit recovery owner.
